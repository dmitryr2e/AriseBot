# ROADMAP.md — План доведения SoloLevelingBot до продакшена

План собран из находок `AUDIT.md` (номера пунктов в скобках — ссылки на аудит).
Фаза 1 = все P0 (блокеры запуска), Фаза 2 = P1 (качество), Фаза 3 = P2 (отложенное).
Внутри фаз работы сгруппированы так, чтобы их можно было выполнять по порядку и коммитить независимо.

## Фаза 1 — Блокеры запуска (все P0)

**Цель:** после этой фазы бот можно безопасно запускать на реальных пользователей и принимать деньги.
**Оценка объёма:** ~3–5 рабочих дней. Небольшие правки, но с миграцией git-истории и настройкой инфраструктуры.

**Статус на 2026-07-27:** ✅ **ФАЗА 1 ЗАВЕРШЕНА.** 1.1–1.5 реализованы и вручную сверены с кодом (см. `AUDIT.md` → «Статус после сессии реализации»). 1.6 выполнена и проверена в браузере. Единственный остаток — ручная чистка git-истории из 1.1, если репозиторий уже был опубликован с БД/токенами внутри (не код-таск, см. `HANDOFF.md`).

### 1.1. Гигиена секретов и данных (AUDIT 2.1, 2.2)
- Удалить `hunter.db`, `hunter.db-shm`, `hunter.db-wal` из репозитория и из git-истории (`git filter-repo`).
- `.gitignore`: добавить `.env`, `.env*`, `*.db`, `*.db-shm`, `*.db-wal`, `__pycache__/`, `*.py[cod]`.
- Перенести путь БД по умолчанию в `data/hunter.db` (создавать каталог при старте).
- Ротировать `TELEGRAM_BOT_TOKEN` и `GEMINI_API_KEY`, если репозиторий когда-либо публиковался.

### 1.2. Платежи: хранение и идемпотентность (AUDIT 6.1, 6.2)
- Новая таблица `payments (id, charge_id TEXT UNIQUE, user_id, payload, amount_stars, created_at, refunded INTEGER DEFAULT 0)`.
- В `on_payment`: `INSERT OR IGNORE` по `charge_id`; выдавать товар только если вставка прошла (rowcount > 0) — идемпотентность при ретраях апдейтов.
- Порядок: сначала записать платёж, потом выдать товар (в одной транзакции).
- Админ-команды: `/payments <user_id>` (история) и `/refund <charge_id>` (вызов `refund_star_payment` + пометка `refunded=1` + откат товара, где возможно).

### 1.3. Надёжность ночного rollover (AUDIT 3.1)
- Обернуть обработку каждого пользователя в `daily_rollover` (и всех массовых джобах) в try/except с логированием.
- Общий троттлер отправки (~20 msg/sec) + обработка `TelegramRetryAfter` (sleep на `retry_after`, повтор).

### 1.4. Деплой и восстановление (AUDIT 5.1, 5.2)
- `Dockerfile` + `docker-compose.yml` (volume для `data/`), либо systemd unit с `Restart=always` — выбрать одну целевую платформу и задокументировать в README.
- Бэкапы: периодический job (`sqlite3 ... ".backup ..."` или `VACUUM INTO`) + выгрузка во внешнее хранилище + ретеншн; документированная процедура восстановления, один прогон восстановления руками.

### 1.5. Минимальный CI (AUDIT 4.1)
- GitHub Actions: `ruff check` + `ruff format --check`, запуск тестов (пока smoke, после Фазы 2 — pytest), `pnpm build` лендинга, `tsc --noEmit`.
- Убрать `ignoreBuildErrors: true` можно уже здесь, если ошибок нет (иначе — Фаза 2, п. 2.10).

### 1.6. Юридический минимум (AUDIT 9.1) — ✅ СДЕЛАНО 2026-07-27

В `game._ensure_today_locked` HP ≤ 0 больше не убивает: выставляется `dying_until = today`, HP фиксируется на 0, уровень и XP не трогаются, `DayEvents.dying` рендерит оффер `texts.DYING` с ценой `REVIVE_PRICE_STARS`. Левелап внутри окна спасает бесплатно (в `grant_xp` HP восстанавливается до максимума). Покупка `revive` в `handlers/premium.py` снимает `dying_until` вместе с HP, иначе просроченное окно всё равно понизило бы уровень.
